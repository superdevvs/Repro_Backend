# Public API errors and restricted diagnostics

API failures retain their HTTP status and return a reviewed `message`, stable `code`, and server-generated UUID `request_id`. Validation failures retain `errors`. Existing product fields remain available, including SMS failure codes, resumable upload state/missing chunks, and service-removal confirmation metadata. Legacy controller envelopes retain their existing fields; the outer API middleware adds correlation and missing envelope fields only.

`X-Request-Id` and `X-Trace-Id` contain the same server UUID. A caller's bounded `X-Trace-Id` is kept separately as client correlation and cannot choose a trace database key. Client telemetry can reference an existing server trace only when that trace belongs to the same authenticated user. Browser session identifiers are scoped to their owner. CORS exposes the two response headers.

Unexpected exceptions receive a fixed message in both debug modes. Explicit application types mark reviewed business messages: `PublicApiException`, `PublicBusinessRuleException`, `PublicConflictException`, `PublicAuthorizationException`, and `PublicApiResponseException`. Compatible base classes keep existing catches working. These types must never wrap an upstream exception message, SQL text, provider body, request headers, or stack. Validation text must also be application-authored. The SMS allowlist preserves the actionable unverified-sender explanation. The offline iGUIDE upload exception preserves its reviewed upload status and details; it is unrelated to inbound provider webhook authentication.

HTTP response exceptions without the reviewed marker retain their status but do not expose arbitrary embedded bodies through the custom renderer. Protocol headers such as `Retry-After` remain available. Authentication challenges and other successful product responses are not rewritten.

Diagnostics record exception class, repository-relative file (or basename), line, and request ID. They omit exception messages, previous exception chains, stack arguments, SQL, credentials, request bodies and provider responses. Logging failure never replaces the API response. Single/daily log files use mode `0660` so the production web and deployment users can share their runtime group. Verify that group membership before provisioning a different host. Old logs are not erased by this change.

The production logging manager also applies a privacy processor to configured, stacked, on-demand and emergency fallback channels. This protects older services/jobs that still pass arbitrary messages or contexts to the logger. It preserves severity, exception class, source location, server correlation and an explicit list of numeric operational facts. Unreviewed labels and arbitrary context/extra fields are discarded. Local and testing logs retain their normal behavior unless a test directly exercises the production processor.

System Overview stores structural payload summaries rather than field values. Backend URLs use matched route templates; unmatched URLs receive a fixed label. Browser URLs use reviewed page routes, without query, fragment or token path values. Client error text and arbitrary error objects are not ingested or broadcast. Historical error/payload displays are redacted when read. Tax document upload/download routes do not collect payload or response telemetry. These changes preserve operational status, timings, page/component activity and correlation, while detailed diagnosis stays with the restricted logger.

The frontend normalizer adds a public error view without replacing the original Axios response, preserving validation and product metadata. Interceptors log no full responses, and production Vite builds remove legacy console/debugger calls so old component logging cannot expose Axios headers or bodies. Verify the production build, not only development behavior.

Bright MLS current and historical results use an explicit public schema. Locally constructed media validation templates remain actionable; upstream diagnostic bodies, payload snapshots, URLs and arbitrary validation text are excluded. The normal publish redirect is regenerated from its manifest ID. Stored raw Bright MLS response data is hidden from generic shoot serialization. Other explicit job/integration failure fields return fixed recovery guidance when historical diagnostics exist.

Square failures expose reviewed decline codes and recovery text (expired card, billing-address or security-code corrections), never SDK diagnostic details. Automation run/step/dispatch histories hide execution context, command output and raw diagnostics, including password-reset links in execution inputs. Step presentation retains operational branch/channel/recipient outcomes. Runtime execution still reads its original private context and output; serialization does not change resumption behavior. New failure records store fixed recovery guidance.

Retired routes: `/ai/test-auth`, `/ai/test`, `/ai/chat-test`, `/debug/user-role`, `/admin/watermark-settings/debug-files`, `/php-limits`, and `/test/mail/*`. The public AI liveness endpoint and the administrator's internal test-shoot assignment tool remain. Integration connection tests and messaging previews/test-send tools remain product features. This change does not change the paused CubiCasa/iGUIDE/Autoenhance webhook authentication rollout or Stripe/Telnyx callback verification.

Focused regressions cover exception canaries with debug on/off, validation and domain messages, status/backoff preservation, logging failure, early error envelopes, manual database/provider failures, trace/session collisions, URL tokens, telemetry storage/broadcast privacy, tax telemetry exclusion, historical Bright MLS data, and frontend metadata preservation. Use the isolated security test base or a release checkout with test-only environment configuration; do not run security fixtures against a production database.
