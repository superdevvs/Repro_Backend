# Listing Studio guest API

The website server calls `/api/external/listing-studio` with a dedicated `X-Studio-Key` and a random 64-hex `X-Studio-Session`. These values never enter browser JavaScript. The website uses a signed, secure, HttpOnly, SameSite=Lax first-party session cookie and enforces same-origin mutation requests. The backend ignores `X-Studio-IP` and arbitrary forwarding headers from this bridge. Visitor IP and the bot check are established by a separate browser request directly to the dashboard, described below. All responses are `Cache-Control: no-store`.

Services are `staging`, `decluttering`, `grass`, `twilight`. JSON successes use `{success:true,data:...}`. Errors use `{message,code,request_id}` with normal HTTP status codes.

- `GET /capabilities`: data `{enabled,services:[{id,label,ready,reason,available}],turnstileSiteKey,limits:{maxFileBytes,globalDaily,ipDaily},stagingOptions:{rooms,styles},allowances:{staging,decluttering,grass,twilight},activeTrialId}`. Allowances are booleans. Staging option objects map supported IDs to labels. A missing challenge configuration disables submission.
- `GET /trials`: data `{trials:[Trial],allowances:{...},activeTrialId}`. Resume the latest active/completed trial after refresh.
- `POST /admissions`: required `Idempotency-Key` (8–64 letters/digits/hyphen/underscore; the website uses a UUID), no upload body. Data `{token,expiresAt,verifyUrl}` with a random 64-hex token and pinned `verifyUrl: "https://reprodashboard.com/api/listing-studio/trial-admissions/verify"`. This token is bound to the server-authenticated guest session and that exact idempotency key; only its SHA-256 hash is stored. It expires after five minutes. Keep it in memory and never put it in URLs or logs. At most three unconsumed live admissions per guest and 1,000 globally.
- `POST /trials`: multipart `image`, `service`, `admissionToken`, optional staging `roomType` and `style`; required `Idempotency-Key` matching the admission. Returns 202 with data `Trial`. Repeating the exact key/image/service/options returns the existing trial before admission expiry/consumption checks and while new edits are paused; a changed payload is 409 `idempotency_conflict`. Only JPEG/PNG/WebP, at most 10 MiB and 40 megapixels. Admission consumption and trial/quota reservation occur in the same serialized transaction; a rejected quota or active-job check leaves the admission unconsumed.
- `GET /trials/{id}`: data `Trial`.
- `GET /trials/{id}/preview`: private, resized, watermarked JPEG bytes. Never forward original/provider URLs. The website proxies these bytes at its own authenticated guest URL.
- `GET /trials/{id}/original-preview`: the same session-bound, resized, watermarked representation of the original; lets a refresh restore the comparison without persisting original bytes in browser storage.
- `POST /trials/{id}/claim-token`: data `{token,expiresAt,claimUrl}`. The claim URL is `https://reprodashboard.com/listing-studio/claim#token=<opaque-token>`; never place the token in a query string or logs. It lasts 30 minutes.

`Trial` is `{id,service,status,progress,previewAvailable,originalPreviewAvailable,downloadAvailable,createdAt,completedAt,expiresAt,error,errorCode}`. Status is `queued|processing|completed|failed|needs_attention|expired`. Progress is a real provider percentage or null. Error is a sanitized string or null and errorCode is a stable string or null; no private paths/provider identifiers are returned. The browser builds its own same-origin preview URL when the respective availability field is true. Full results are never available through the guest bridge.

Before submitting a new photo, the website generates one idempotency UUID and follows these steps:

1. Its same-origin BFF mints an admission with `POST /admissions` using that UUID and the existing HttpOnly guest cookie.
2. The browser calls the returned dashboard URL directly with JSON `{token,challengeToken}`, `Content-Type: application/json`, and `credentials: "omit"`. It sends no dashboard auth or bridge secret. The Turnstile widget action is `listing_studio_trial`.
3. After `{success:true,data:{verified:true,expiresAt}}`, the browser submits the image through its existing BFF with `admissionToken` and the same idempotency UUID. Neither upload nor previews move to cross-origin browser requests.

Only `POST /api/listing-studio/trial-admissions/verify` permits this browser CORS access. Exact HTTPS origins derive from configured Turnstile hostnames; no subdomain wildcard, HTTP origin, arbitrary port, cookie credentials or Authorization preflight is accepted. Origin must also match the verified Turnstile hostname. OPTIONS is handled before generic API CORS; all other API origins remain unchanged. The JSON body is capped at 4 KiB before parsing. Verification is limited to 20 attempts per observed IP per minute. Siteverify calls occur outside database transactions and use a saved UUID to safely retry a lost response; already verified same-IP retries do not consume another challenge.

Production ingress was inspected on 2026-10-31: nginx passes the TCP peer as FastCGI `REMOTE_ADDR` and has no real-IP rewriting directives. `ListingStudioVisitorIp` accepts `CF-Connecting-IP` only from the explicitly configured Cloudflare CIDRs, rejects Worker subrequests and Cloudflare's shared Worker sentinel, and otherwise uses the socket peer while ignoring forwarded headers. This trust boundary is at infrastructure we control, independent of Lovable runtime/header behavior. Only an HMAC IP hash is stored; raw IP is used transiently for Turnstile validation. Reassess this helper if the origin proxy topology changes.

Admission errors are `trial_admission_invalid` (422: unverified, consumed, missing, wrong session or wrong idempotency key), `trial_admission_expired` (410), `trial_admission_limit` (429), `trial_ip_unavailable` (403), `trial_origin_invalid` (403), `trial_challenge_failed` (422), `trial_challenge_unavailable` (503), `trial_rate_limit` (429), and `trial_unavailable` (503). Challenge failures never consume a guest service allowance. The kill switch blocks minting, verification and new starts. Preserve the idempotency key and uploaded bytes across uncertain upload responses; do not mint a new job merely because the response was lost.

Dashboard endpoints retain Sanctum, active-account and client checks, but the three named routes below do not require email verification:

- `POST /api/listing-studio/trials/claim` with `{token}`: atomically links the guest session's jobs to the signed-in client. Data `{trials:[Trial]}`. A same-client replay succeeds. Different-client ownership gives 409 `claim_conflict`; expired token gives 410 `claim_expired`; previously consumed client service allowance gives 409 `trial_allowance_used`.
- `GET /api/listing-studio/trials`: data `{trials:[Trial]}` for the authenticated client, allowing refresh after the claim token is consumed.
- `GET /api/listing-studio/trials/{id}/download`: authenticated owner-only binary attachment. Use a bearer-authenticated fetch and local blob URL, never put an auth token in a URL.

One successful free result per service and guest/client; one active job per session. Global 100 and IP 12 starts per rolling 24 hours include failed starts. Confirmed failures release the service allowance; ambiguous submissions remain reserved. Unclaimed media expires after seven days. Existing team-delivered free edits and paid credits are separate.

Operational configuration is in `config/listing-studio-trials.php`: trials default disabled, bridge key must be at least 32 characters, Turnstile secret/public key and exact allowed hostnames must all be configured. No additional secret or dashboard browser authentication is required for admission. `listing-studio:prune-guest-trials` runs hourly to reconcile interrupted bookkeeping, expire unclaimed media and remove expired admission rows. `listing-studio:resume-trial {id}` only resumes an existing confirmed provider operation; it never creates a new editing job. Never automatically retry `needs_attention` with a new idempotency key.

Each service has a release gate: `LISTING_STUDIO_STAGING_TRIALS_ENABLED`, `LISTING_STUDIO_DECLUTTERING_TRIALS_ENABLED` and `LISTING_STUDIO_TWILIGHT_TRIALS_ENABLED` default false; `LISTING_STUDIO_GRASS_TRIALS_ENABLED` defaults true. A real smoke on 2026-10-31 completed technically but changed permanent cabinetry/light fixtures for staging, removed furniture for decluttering, and produced an unusably dark twilight. Grass preserved the property. Keep failed services unavailable until reviewed real outputs pass preservation and quality checks. Capability responses mark a gated service unready/unavailable; new upload reservations and worker submissions reject it without consuming a new entitlement. Accepted provider jobs may still be retrieved.

New staging trials use add-furniture-only with removal off, so the VSAI request omits `remove_furniture`. This follows the provider's [v2 staging configuration](https://docs.virtualstagingai.app/v2-api/endpoints); it removes the explicit empty-room step, but does not guarantee preservation by a generative model. Validate it on vacant rooms and inspect all permanent features before opening the gate. Occupied-room furniture replacement is not validated by this recipe. Ordinary staff Studio options are unchanged; an old guest recipe with automatic removal cannot start another paid submission.

Decluttering and twilight trials snapshot the supported `fal-ai/nano-banana-pro/edit` route, one 2K image, while ordinary Studio routes remain unchanged. Their initial FLUX output failed visual review: the existing Autoenhance intermediate retained furniture, identifying the specialist edit as the destructive stage. The fixed declutter instruction preserves furniture and intentional cushions/rugs/artwork/lamps/decor and requires no changes when defined loose clutter is absent. Twilight adds a fixed bright early-blue-hour instruction requiring readable facade/lawn, natural sky and warm existing lights without property changes. Existing accepted checkpoints retain their original route and prompt for retrieval; no pending job is silently switched to another paid model. This recipe change requires real visual validation and does not itself open either service gate.
