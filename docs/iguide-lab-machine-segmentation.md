# Machine staging segmentation candidate

This internal executor consumes source-bound machine selections. It does not expose an HTTP start route, create a human-reviewed `IguideLabMask`, accept an edited panorama, or change the legacy grass pipeline. Its `LabMachineSegmentationAuthority` interface deliberately has no application binding until a separately typed, completed placement-assessment record is integrated. A boolean in `step.data` or a client request is not an assessment authority.

Dependencies are the durable workflow/step/invocation services and a trusted assessment loader implementing the exact assessment protocol. The current workflow PR supports lighting; its two-analysis limit is unchanged. Staging needs a separately reviewed three-analysis/assessment policy. This candidate does not make staging available by itself.

The trusted workflow reserves `kind=segmentation` with protocol `automatic-staging-segmentation/1`, actual `sectionId` and `candidateRunId`. Its persisted step UUID is the only request identity. The authority must load and validate the completed machine assessment, exact native/cut/submitted-source/candidate/parent-context/geometry/analysis/settings bindings, and return that assessment's plan after injecting the reserved UUID. The protocol's sorted-JSON `inputFingerprint` and the workflow's reservation digest are distinct. A committed Python-produced synthetic fixture checks their plan compatibility without claiming a real inference result.

Two initial calls are supported: original-cut `floor` with one box/mask, then exact-candidate `furniture` with three boxes/masks (sofa, chair, coffee table). The floor receipt must have a successful operational association and unchanged saved mask before furniture can spend. Both inputs are owned, completed 2048-square section/run records and are rehashed and decoded before any paid claim. The original preparation must reproduce the image run's saved source hash. Unsupported plan fields, model, dimensions or options stop before submission.

The shared workflow cancellation transaction and paid claim use the same project write lock. The claim is durable before the single POST. There is no POST retry or alternate Fal credential. A timeout, ambiguous response or worker crash after claiming and before saving a receipt requires attention. A known receipt resumes GET polling/download only, bounded to 30 minutes. The provider receipt is saved before disk writes. Raw responses, individual raw PNGs, exact hashes, decoded positive area and exclusive pixel bounds are retained privately. Array order never establishes object identity; the trusted protocol separately computes unique association and can stop on missing, merged or ambiguous masks.

Provider schema is the verified `fal-ai/sam-3-1/image` box-prompt API. Queue model/URLs are fixed. Media downloads allow HTTPS `fal.media` subdomains only, public DNS addresses pinned to the request, no proxy or redirect, bounded time and streaming bytes. Responses are capped at 1 MiB and masks at 8 MiB each. Mask PNGs must fully decode at2048-square, opaque equal grayscale channels,8-bit and single frame. Actual score/box metadata stays in the raw provider result; normalized bounds are computed from decoded pixels. Unknown usage/cost remains null.

`IguideLabMachineSegmentation` and its private files are machine evidence, never user confirmation. Terminal outputs are `completed` (ready only for support validation), `needs_review`, `needs_attention` or `failed`. Every result explicitly records no human review and no automatic acceptance. No provider calls were made while building this candidate.

Known-receipt resume revalidates the completed assessment plan and actual source/candidate bytes before operational association. The authority bridge must also reload its typed assessment in `associate()`; a cached plan alone cannot authorize support. A changed input retains its provider receipt and stops without another POST.
