# Prospective source layout candidate

This candidate is disabled by default. It separates a plausible source-only furniture proposal from proof about generated furniture. It does not change the actual placement, segmentation, support, native composition, or independent full-sphere quality gates.

## Route and budget

1. The existing receipt-bound original framing analysis must return a framing candidate. A blocked original source remains held.
2. Extract that exact source-native 2048 square view and send the actual cut plus the five existing same-capture parent views to the new `scene-instructions-staging-layout-1` recipe.
3. Request an explicit prospective layout: exactly one sofa, one coffee table, and one chair, their floor footprints and complete-object envelopes, visible floor regions, forbidden floor, protected fixed features, and required routes. These are model-authored hypotheses, never masks or measured dimensions.
4. If unresolved source evidence is potentially observable, the initial result may request **one** adaptive operation: either one or two native optical/floor detail projections, or one reframe of the complete group. The next analysis receives the original questions and full prior result, exact new evidence, and its hashes. It must return a draft candidate or a hold.
5. A supported prospective plan permits one image request. The separate actual placement assessment still checks realized size, all visible feet, margin, foreground ordering and optics before the two SAM requests. Local support and native composition remain unchanged. Final visual evaluation must inspect all seven paired sphere boards.

Maximum child reservations are four analyses (original framing, initial layout, optional layout follow-up, actual placement), two source sections, one image, two segmentations, one composition, and one evaluation. Each analysis may use only the existing explicit quota fallback; transport uncertainty never authorizes a duplicate request. The adaptive choice has one stable durable step UUID. Replaying changed input is rejected.

## Source evidence and geometry

The edit cut is the sole generation target. Parent images and optional `source_detail_1` / `source_detail_2` are projections of the same original capture; they are not independent camera evidence. Details are 1024 square and extracted directly from the immutable native, with explicit yaw, pitch, and horizontal field of view. They cannot expand the edit scope.

The typed context separately binds the native SHA, raw extracted cut SHA, actual GD-prepared source SHA, source geometry SHA, original framing result SHA, and prior layout result SHA. Original source/cut/parent files, raw paid responses, provider execution IDs, and source poses are revalidated before every analysis attempt and image claim. A changed prior receipt cannot authorize a follow-up or image.

Finite convex polygons, nonintersecting footprints, visible-floor containment, route and fixed-feature conflicts, and the ten-percent envelope margin are checked mechanically. Touching ambiguous boundaries holds. These checks cannot certify that a model identified the floor correctly or that a proposed scale is physically calibrated. All returned `realizedPlacementVerified`, `geometryVerified`, `supportMaskAuthority`, and `manualAcceptance` fields remain false.

## Optical limits

Glazing presence alone does not establish a required reflection, and cropping glazing out does not establish its absence. The assessment must relate observed apertures and floor appearance to the specific prospective group. Low-resolution or oblique evidence is allowed to remain uncertain. Details may resolve visible material or aperture questions; they do not recover hidden geometry or exact reflection physics.

The supported compositor supplies opaque furniture plus tiny original-floor contact attenuation. Required reflections, transparent furniture, broad directional shadows, hidden receivers, occupied rooms and unresolved foreground relationships hold. No new source lighting, reflection or placement synthesis is hidden in this update.

The existing original framing protocol can still hold before a cut, including Lifestyle's observed glazing-related block. This candidate does not reinterpret such a block. A later reusable pre-cut resolver would need an explicit typed `needs_optical_detail` result, cited source aperture, bounded prospective placement region, exact native detail requests, a separate durable budget, and an owned follow-up result. Confirmed unsupported dependencies must remain held. Actual generated person/furniture position must always replace the proposed position during the later assessment.

## Runtime and validation

`LabStagingLayouts` binds its PHP owners, recipe, source-detail worker, geometry code, configured interpreter bytes, and pinned Python / NumPy / Pillow versions. `staging_layout_details.py` is source-only, has no provider interface, checks private paths and immutable input/output hashes, and atomically publishes replayable results with 2770 directories and 0660 files. The existing math/composition/QA workers are unchanged.

Current local tests use fake provider HTTP and synthetic diagnostic images. They are protocol/lifecycle tests, not autonomous real-scene success. The candidate must remain unavailable until a separate exact-tree pinned Linux detail/integration proof, actual DTO compatibility check, and release review have passed. No production activation or provider request is part of this candidate preparation.
